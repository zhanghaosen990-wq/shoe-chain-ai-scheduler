# 鞋链智排 · 双端协同制造平台

基于 React 19 / React Router 7，Node 本地 API 管理演示账号、订单、工厂资料与评价。原有 BOM 识别与 Agent 排期页面保留，并嵌入品牌工作台。

## 启动

双击项目根目录的 `启动原型.command`，自动构建前端并启动服务；打开 http://localhost:4173 。保持终端窗口开启。

已安装 Node / npm 的环境可执行：

```sh
npm ci
npm start
```

`npm start` 会先构建。开发后可用 `npm run build` 重新生成页面资源，再刷新浏览器。运行 `npm test` 检查业务逻辑。

## 页面与演示账号

| 路径 | 用途 |
| --- | --- |
| `/` | 欢迎页与品牌 / 工厂入口 |
| `/brand` | 品牌订单、合作工厂与历史评价 |
| `/brand?view=publish` | 原有 BOM 与 Agent 排期系统 |
| `/factory` | 工厂产能管理、接单、运营指标与评价 |
| `/profile/:id` | 品牌或工厂公开主页 |
| `/workspace` | 保留的原版需求发布页面 |

导航栏提供“登录”“注册账号”。登录后显示企业名称、资料菜单与退出按钮。首次打开时将以下账号写入 localStorage，初始化不会覆盖已编辑资料：

| 账号 | 密码 | 企业名称 | 身份 |
| --- | --- | --- | --- |
| brand_01 | 123456 | 迈斯特时尚服饰 | 品牌方 |
| brand_02 | 123456 | 云端鞋履设计室 | 品牌方 |
| factory_01 | 123456 | 瓯越精工鞋业有限公司 | 工厂端 |
| factory_02 | 123456 | 楠江鞋业制造有限公司 | 工厂端 |

注册时必须选择身份，填写账号、至少 6 位密码及企业名称；成功后自动登录。用户名支持 3–32 位字母、数字、下划线（含手机号），不区分大小写且不可重复。新账号使用独立 ID，不继承测试账号订单。

未登录访问工作台或直接打开 /brand、/factory 时返回首页并提示登录；已登录账号访问另一角色工作台会返回自身工作台。刷新恢复登录，退出后不再可访问受保护页面。公开企业主页允许访客查看。

在企业名称菜单或自己的主页选择“编辑企业资料”，可修改企业名称、联系人、电话、主营品类及优势说明，保存后导航和主页同步更新。工厂产能表单与企业资料共用品类和优势说明。

账号与 Profile 使用 localStorage 的 shoe-users-v1，登录用户 ID 使用 shoe-session-v1；旧 shoe-account 不再用于身份。密码保存为随机盐加 SHA-256 摘要，不以明文保存。公开企业资料同步本地业务 API，不上传密码摘要。

这是按需求实现的浏览器本地账号与前端路由保护，账号不能跨设备自动同步，也不提供服务端认证安全边界；后端 Profile 同步接口信任本地账号身份。正式部署需替换为服务端账户、密码哈希和会话认证。

推荐流程：登录 brand_01 → 在完成订单中评价工厂 → 编辑企业资料 → 退出并登录 factory_01 查看评价；也可注册新品牌或工厂，验证空白主页、资料与产能保存。

## 数据与指标

数据预置 2 个品牌、3 家工厂和历史合作记录。首次修改后保存到 `data/portal-state.json`，重启保留；该文件被 Git 忽略。测试可设置 `PORTAL_STATE_FILE` 指向临时数据文件，不影响演示数据。

履约率、合格率来自明确标注的模拟历史样本；评分按已保存评价取平均。未来 10 天可用产能 = 日均产能 × 10 − 生产中订单数量（最低 0）；待接单不占用产能。此模型用于演示，不含节假日、复杂交期或真实排产约束。

保存工厂资料和订单状态时同步 Agent 工厂能力与产能。工厂只能保存当前账号的资料；品牌只能评价自己的已完成订单，服务端拒绝重复评价和越权订单变更。

## 图片与 Excel 识别

工厂页面支持 XLSX / JPG / PNG 资料，最大 20MB；点击“一键识别”调用现有 DeepSeek 服务端接口并回填设备、工艺、品类、MOQ、日均产能。缺失字段保留原值，识别后需要校对并保存。产品细节图支持最多 6 张 JPG / PNG，单张 2MB，支持预览与删除。

在项目根目录 `.env` 中设置：

```dotenv
AI_PROVIDER=deepseek
DEEPSEEK_API_KEY=你的密钥
AI_MODEL=deepseek-chat
# 图片识别需使用账号实际支持视觉输入的模型：
# DEEPSEEK_BOM_MODEL=可用视觉模型
```

密钥仅由服务端读取。XLSX 提取文本后调用模型；图片以 image_url 输入。图片识别是否可用取决于配置模型的视觉能力，接口不支持时页面展示错误，可手动填写，不会生成虚假识别结果。语义增强需要有效 API 配置；无配置时仍可关键词推荐及手动选厂。

## 智能推荐与工厂确认订单

品牌在 BOM 与 Agent 页面填写需求，点击“智能推荐工厂”。推荐结合品类、部分工艺词条与模型语义排序，不要求描述逐字一致。已登记的工艺与待确认项分开展示；模型只选择数据库中已有工厂，展示依据来自实际工厂资料，不展示模型自行生成的价格或设备承诺。

选择工厂并分配数量 → 核对风险 → 提交给所选工厂。支持单厂整单或多厂拆单，总数必须一致。无报价、MOQ / 产能风险和自动排期失败不阻止提交；模型未配置或调用失败时保留关键词推荐，也可展开全部工厂手动选择。

工厂在“合作订单与排期”点击“查看需求 / 处理”，查看完整 BOM、样品图、数量、交期、合作方式及备注。确认承接后计入产能；拒绝需填写原因。品牌可对被拒绝的部分重新选择工厂，原拒单记录和其他工厂的订单保留。所有新分单携带共同需求组 ID，保存需求快照；旧订单缺失字段显示“未提供”。

`/api/agent` 返回 `candidates`、`mode`（semantic/rules/fallback）、`notice`、工厂快照及辅助排期。`/api/portal/orders` 必须包含 `requestId`、`title`、`demand` 和 `allocations`；重分配额外提供 `reassignOrderId`。重复的提交标识与相同内容仅返回已有结果，不重复建单；成功提交后该次分析入口锁定，创建新需求需重新分析。

订单状态：pending → production → completed，或 pending → rejected。`/api/portal/order-status` 拒绝时提交 `reason`；接单有 MOQ / 产能风险时须提交 `confirmRisks: true`。当前仍采用本地账号身份，不改变既有认证边界。

运行 `node app/verify-order-flow.cjs`（需 Playwright / Chrome）会在独立 4175 服务和临时数据中验证实际 API 下单、400/400 拆单、工厂接单与拒单、拒绝部分重分配、重复提交、需求变更失效、完成评价和移动端布局。测试不调用外部模型，也不修改正常使用的数据。

## 工厂新订单提醒

工厂登录、刷新或重新进入 `/factory` 时，有本人 `pending` 订单就会自动弹出待接单提醒。卡片显示品牌、款式、本厂分配数量、目标交期与合作模式；普通订单可“立即接单”，MOQ / 产能有风险时需确认后接单。“拒绝 / 协商”要求填写原因，提交后标记为 rejected 并同步品牌。“查看详情”关闭提醒并定位、高亮对应订单行。

顶部铃铛仅对工厂账号显示，数字始终等于当前工厂未处理订单数，关闭提醒不会清零。关闭后同一批订单不随轮询重复弹出；新增订单、刷新或重新进入工作台会提醒。已有其他业务弹窗时，新订单提醒会等该弹窗关闭后再显示。

本地 API 仍是订单权威来源，前端将不含图片/BOM 大字段的订单摘要同步到 localStorage `shoe-orders-v1`，保留真实 `pending` / `production` / `rejected` 状态。跨标签页通过 storage / BroadcastChannel 触发刷新，切回窗口或标签页立即刷新；停留页面另有 15 秒轮询。缓存写入失败不影响已成功的接单操作。

运行 `node app/verify-order-alerts.cjs`（Playwright / Chrome）会使用独立 4176 服务及临时数据，验证登录、刷新、切回、轮询、跨标签通知、数量同步、关闭重开、接单、拒绝、风险确认、定位和移动端显示，不修改正常订单数据。

## 履约反馈与动态工厂指标

品牌对本人已完成订单点击“填写履约反馈 / 评价工厂”。交货、质量与星级必选且不默认选择，文字可留空（最多 500 字）。历史真实评价可原位补填一次；示例评价保留展示但始终排除统计，完整问卷不可重复提交。

工厂工作台与主页使用累计完整问卷计算，均保留一位小数，无数据返回 null：

- 交货选项为 100 / 90 / 70（按时、延期 1–2 天、延期 3 天及以上），按提交时本厂分单数量加权。这是问卷履约得分，不是严格准时订单占比。
- 质量代表值为 99.5 / 96.5 / 92 / 85，按反馈笔数平均，显示“问卷估算”，不是实测抽检百分比。
- 综合星级按完整问卷等权平均。第四张产能卡保持实际保存产能与生产中订单的独立计算。

`app/feedback.js` 是前后端共享统计模块。`POST /api/portal/reviews` 接收 `orderId, delivery, quality, rating, comment`；服务端保存 `feedbackVersion: 1`、`feedbackSubmittedAt` 和不可由客户端指定的 `orderQuantity`。`GET /api/portal` 返回权威 analytics。前端在 `shoe-feedback-v1` 缓存评价及工厂指标，缓存失败不影响保存；storage、BroadcastChannel、窗口焦点及 15 秒轮询刷新，分析进行中另每 2 秒刷新。

问卷先保存，随后使用现有 AI_PROVIDER / AI_MODEL / 供应商密钥异步分析文字。仅保留最多 5 个 highlight / risk 标签及逐字原文依据；不影响固定答案和 KPI。空文字为 skipped；超时、缺少配置及格式错误为 failed，原品牌方可通过评价卡“重试标签分析”（`POST /api/portal/reviews/:id/analyze`）重试。成功为 completed；服务重启将遗留 pending 转为可重试 failed。无伪造标签兜底。

`node app/verify-feedback.cjs` 使用独立 4177 服务及临时数据验证 300/700 分单对应 93.0%、98.0%、4.5 星，必选校验、补填防重、账号与订单限制、失败标签重试、工厂主页/缓存同步及重启持久化。`npm test` 包含模型成功、异常、真实超时、原文依据过滤及并发重试测试，模型使用测试替身，不依赖外部供应商在线。

## 前端视觉与交互

首页、品牌端、工厂端、企业主页、登录弹窗与 BOM 发布页共用 `app/ui/tokens.css`：暖白背景 `#F9F8F6`、白色卡片、轻边框与柔和阴影，主色为科技蓝 `#2563EB`。成功、警告、错误保留语义色；不提供深浅主题切换。品牌与工厂桌面 Header 均为 64px，BOM 独立页沿用相同视觉规范，嵌入时隐藏重复 Header。环境粒子仅在首页展示，工作台保持安静、清晰的业务界面。不依赖外部动画库或远程字体。移动端订单以卡片展示，01–04 步骤导航始终保持横向单行。

品牌发单保持连续表单，顶部 `01 上传 → 02 解析 → 03 需求 → 04 执行` 根据实际操作更新。点击步骤可定位到对应区域；手动补齐必需 BOM 字段也可以直接继续。修改需求后需要重新分析。

BOM 区的“一键填入演示数据”支持商务男鞋和女装，使用随项目提供的 PNG 设计示意图和预置字段，不调用模型、不自动下单。填充后明确标注“演示数据 · 预置结果”，可撤销回到原草稿，也可点击原识别按钮调用真实接口。演示图片仅作需求演示，不代表已核实的物料或工厂能力。

评价问卷支持填入演示答案和撤销；提交仍需用户操作，提交后按现有规则计入该订单工厂的指标。已提交问卷不能重复提交。

操作结果通过右上角 Toast 显示，移动端显示在顶部；通知支持手动关闭、键盘访问及悬停暂停。弹窗打开时也能看到通知。表单仍打开时，失败原因在表单中显示；已关闭时，失败通知可重新打开并恢复草稿。草稿只保存在当前页面内存，不跨刷新保存。

Esc 关闭当前最上层弹窗，已经提交的请求继续执行；重新打开同一表单可看到处理中状态，完成后同步关闭。单行表单可按 Enter 提交或进入下一步；多行文本保持换行，中文输入法确认不会提交，风险确认不能跳过。

`/workspace` 可独立使用；品牌页通过同源 iframe 嵌入，自动同步内容高度、步骤定位和通知。新增静态资源仅开放 `app/ui/` 中明确列出的脚本／样式与两张演示图片。

### 暖白主题与首页动画回归

`node app/verify-theme.cjs` 默认使用独立 4184 服务及临时业务数据；`verify-dark-ui.cjs` 保留为兼容入口，执行同一套暖白主题验证。设置 `BASE_URL=http://localhost:4173` 可只读检查实际开发服务。检查共享资源、暖白背景与白色卡片、统一 Header、按钮、表单、非首页无 Canvas，以及 360／390／768／1280／1440／1920px 门户与 iframe 内容边界。截图保存到 `outputs/warm-theme/`。

修改服务端静态资源白名单后需要重启原有 `node app/server.js` 进程；只构建前端不会更新正在运行的服务代码。未带版本号的静态资源使用 `Cache-Control: no-cache`。

首页“让好设计，遇见好制造。”采用可选择、可访问的两行 DOM 文字，分别以深灰与科技蓝展示。两行文字淡入并上移 10px，错开 120ms；说明和入口在一秒内显现，独立于粒子进度。Canvas 不绘制文字、不拦截交互。粒子构图位于标题上方中央，随首屏滚动退出；下方主题段落保持暖白底和深灰／蓝色文字层次。

每次刷新或重新进入首页，淡蓝粒子从首屏散落状态开始，约 2.8 秒汇聚为有鞋底、鞋面和鞋带的鞋形，停留 5 秒，经过 2.4 秒变为供应链网络，再停留 5 秒并用 2.4 秒变回鞋形。后续循环直接形变，带有轻微漂浮和鼠标避让、弹性归位。点击“跳过动画”立即显示首屏并聚焦品牌入口，原身份路由与登录流程不变。

首页桌面约 900 个粒子、窄屏 450 个；目标路径统一维护，逐帧计算为线性复杂度，绘制上限约 30fps，设备像素比最高 1.5。首屏完全离开视口或标签页进入后台时暂停，返回后继续当前进度；尺寸改变只重新计算位置。系统开启“减少动态效果”时直接显示清晰文字和静态鞋形；Canvas 不可用时标题和业务入口仍正常使用。

`node app/verify-landing.cjs` 默认运行独立 4187 测试服务，可通过 `BASE_URL` 检查其他服务，只发送业务读取请求。覆盖独立 DOM 入场、提前可用的入口、鞋形／网络转换、鼠标交互、滚动暂停与恢复、刷新、跳过焦点、390／768／1280／1440／1920px、桌面短屏、减少动态效果和 Canvas 失效降级。截图保存到 `outputs/warm-theme/`。`app/test/landing-particles.test.js` 验证形变时间线、目标分布、鼠标排斥归位、尺寸变化及静态模式。

### 品牌工作台 · 履约总览

`/brand` 沿用全站暖白背景、白色内容面与蓝色主操作。标题、履约概况、近期订单逐层进入；系统开启“减少动态效果”时直接显示。保留已有信息结构、导航、筛选、抽屉与嵌入发布流程。

- 总览：进行中 = 待接单 + 生产中；历史发单、合作工厂、累计评价缩为辅助指标。履约分布使用全部订单的真实状态，点击数字或状态即可下钻。
- 最近更新：按订单 `updatedAt` / `createdAt` 降序展示 5 笔。需要关注只显示可重新分配的拒单与可提交／补填的评价，示例或已完整评价、已重新分配订单不重复提醒；首页最多展示 3 项，其余在关注抽屉中查看。
- 订单管理：搜索款式、订单 ID、需求组 ID 和工厂名称，结合状态筛选，每页 10 笔。筛选、搜索、页码保存到 URL，刷新和关闭详情不丢失条件。
- 订单详情：右侧抽屉沿用需求快照，可确认完成、重新分配与填写履约评价；Esc 或关闭按钮返回原位置，并恢复键盘焦点。
- 合作工厂每页 9 家；履约评价每页 6 条。发布页切换到其他品牌分页后保留 BOM 草稿。

### 工厂工作台 · 四个视图

`/factory` 默认显示工厂概览：四项真实指标和最多三条近期订单（待接单优先），详细指标口径按需展开。企业名称下方提供与品牌端一致的下划线导航，选中项为科技蓝：

- `?view=orders`：订单状态筛选、品牌／款式／订单搜索，每页 10 条。排期使用已有目标交期、生产中数量与估算工作量；不提供虚构工序进度。履约评价进入抽屉，每页 6 条。
- `?view=capacity`：基础产能、擅长品类、设备和工艺；资料导入及候选工艺按需展开。
- `?view=showcase`：介绍与产品细节图。每个视图仅在顶部提供一个主要操作按钮。

两个编辑器访问后保持挂载；Tab 切换和后台同步保留未保存草稿。刷新或离开工作台后重新读取已保存资料。保存失败保留输入；识别期间可切换 Tab，返回查看回填结果。搜索／筛选／页码写入 URL，浏览器前进后退恢复视图。订单通知使用 `?view=orders&order=<id>` 清除阻碍定位的筛选、切换目标页并聚焦对应行。

`POST /api/portal/factory` 新增可选 `section`：`capacity` 仅校验更新品类、MOQ、日均产能、设备、工艺；`showcase` 仅校验更新介绍与图片，新工厂无需先完成产能资料。两组使用字段白名单，省略 `section` 保持原整表保存，未知分组报错。响应仍是完整快照，前端以保存响应同步本地账号品类和介绍，无数据迁移。

构建后运行 `node app/verify-factory-tabs.cjs`（旧 `verify-factory-workspace.cjs` 为兼容入口）。独立 4188 服务与临时数据验证导航、草稿、独立保存、失败重试、图片、识别跨 Tab 回填、通知跨页定位、评价抽屉、新账号隔离以及六种屏宽的全部视图。仅外部识别和失败情境使用替身。截图保存在 `outputs/factory-tabs/`；1440×900 下检查概览核心内容首屏可见。`verify-order-flow.cjs`、`verify-order-alerts.cjs`、`verify-portal.cjs` 和 `verify-brand-workspace.cjs` 继续覆盖完整业务链路。
